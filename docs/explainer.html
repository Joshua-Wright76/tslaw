tslaw
Proofs for TypeScript functions, checked by Z3
How it works, in about two minutes
The idea

A test checks some inputs. A law covers all of them.

Tests: 4 inputs, all passThey only cover the cases you thought of.
Law: one input breaks itThe bug was sitting where nobody looked.
Each dot is a possible input. Your tests try a handful. A law is a claim about every input, including the ones you forgot. tslaw checks laws with a theorem prover, so nothing is left out.
What you write

Ordinary TypeScript, plus laws

"use verified";import { law, implies } from "tslaw/runtime"; type Result = { readonly from: bigint; readonly to: bigint };export function transfer(from: bigint, to: bigint, amount: bigint): Result { if (amount > from) return { from, to }; return { from: from - amount, to: to + amount };} law("balances never go negative", (from: bigint, to: bigint, amount: bigint) => { const next = transfer(from, to, amount); return implies(from >= 0n && to >= 0n, next.from >= 0n && next.to >= 0n);});
One line opts the file in. Everything else in your project is untouched. Your functions are plain TypeScript. This one moves tokens between two balances. A law is a function that must return true for every possible argument.

Stage 1

Type check

The proof assumes the types are true, so they have to be.

strict noUncheckedIndexedAccess exactOptionalPropertyTypes
Imports are checked tooEvery verified file this one imports goes through the same check.
// @ts-ignoreComments that silence the type checker are rejected.
This is the regular TypeScript compiler. No fork, no new syntax.
Stage 2

Only code that math can describe exactly

Allowed

Rejected, and why

What's left after this check is a small, predictable slice of TypeScript. Anything the translation can't get exactly right is refused, not guessed at. That refusal is the point: a proof about an approximation would be worthless.
Stage 3

Translate TypeScript into logic

Your TypeScript
type Result = { readonly from: bigint; readonly to: bigint;};function transfer( from: bigint, to: bigint, amount: bigint,): Result { if (amount > from) return { from, to }; return { from: from - amount, to: to + amount };}law("balances never go negative", (from: bigint, to: bigint, amount: bigint) => { const next = transfer(from, to, amount); return implies(from >= 0n && to >= 0n, next.from >= 0n && next.to >= 0n);});
What Z3 receives (names simplified)
(declare-datatypes ((Result 0)) (((mk (from Int) (to Int)))))(define-fun transfer ((from Int) (to Int) (amount Int)) Result (ite (> amount from) (mk from to) (mk (- from amount) (+ to amount))))(declare-const from Int)(declare-const to Int)(declare-const amount Int)(assert (not (let ((next (transfer from to amount))) (=> (and (>= from 0) (>= to 0)) (and (>= (from next) 0) (>= (to next) 0))))))(check-sat)
A readonly record becomes a datatype. A bigint becomes a true mathematical integer. A function becomes a definition. if becomes ite: if-then-else. The law's parameters become unknowns. Z3 is free to pick any values for them. The law itself is wrapped in not. That one word is the whole trick.
Stage 3

Ask Z3 to break the law

“Is there any input that makes this law false?”
Z3 answers: unsat

No such input can exist.

PROVED
Z3 answers: sat

Yes, and here it is.

DISPROVED + counterexample
Proving “always true” directly is hard. Searching for one failure is what solvers do. If no failure can exist, the law holds for every input. That is a proof. If one exists, Z3 hands back the exact values. Z3 doesn't try inputs one at a time. It reasons about all of them at once, with algebra.
In practice

The transfer function has a bug

$ tslaw check transfer.law.ts DISPROVED "balances never go negative" Counterexample: from = 0n, to = 8855n, amount = -8856n
transfer(0n, 8855n, -8856n)
→
{ from: 8856n, to: -1n }
// fix: if (amount <= 0n || amount > from) return { from, to }; PROVED "balances never go negative"
Nobody wrote a test with a negative amount. Z3 found one anyway. Run it for real: a negative transfer pulls the receiver below zero. Add the missing check, and the same law is proved for every input.
Trust

What keeps PROVED honest

Random runsEvery proved law is also run in real JavaScript on hundreds of random inputs.
Replayed failuresEvery counterexample is run for real and must actually break the law.
A file per past bugEach way tslaw was once fooled is kept as a test that must never pass again.
It proves your laws, not that you wrote the right laws.
law() does nothing at runtime. The checking all happens before you ship.
Unverified callers aren't checked, unless they go through a generated guard.
A proof is only as good as the translation, so the test suite cross-checks it against real runs. And a proof has limits worth knowing.
More than arithmetic

The same question, asked of bigger code

Contractsrequires is proved at every call. ensures is proved for every input that meets it.
Recursion and loopsEach states a measure that shrinks, so it provably ends. Loops also state an invariant.
ArraysEvery at(xs, i) is proved to be in range before the code ever runs.
A second solver. --cross-check has cvc5 confirm each verdict.
Guards. tslaw guard writes runtime-checked entry points for other callers.
A proof of the prover. For the core language, the translation is proved correct in Lean.
"Can any input break this?" also works for functions that call, loop and index. And three things reduce how much you take on trust.
